## 一、设计说明

### 1.1 技术选型

| 层级 | 技术方案 | 说明 |
|------|---------|------|
| 数据库 | MySQL / PostgreSQL | 关系型，MVP足够 |
| 后端 | FastAPI | Python原生，和AI链路无缝衔接 |
| AI | Dify API / OpenAI API | LLM调用 |
| 文件存储 | 本地 / 对象存储 | 证据文件 |
| 向量库 | FAISS | RAG知识检索（独立于关系库） |

### 1.2 设计原则

```
1. MVP可落地 —— 不设计企业级几十张表，只做核心链路
2. 产品思维 —— 体现"案件→证据→报告"业务闭环
3. AI可评估 —— 用ai_task表记录每次AI调用，支持效果评估
4. 可扩展 —— 表结构留有余量，后续加字段不影响核心链路
```

### 1.3 核心业务链路

```
用户(user)
    │
    │ 1:N
    ▼
案件(case_case) ──────┐
    │                  │
    │ 1:N              │ 1:N
    ▼                  ▼
证据(evidence)    AI分析报告(ai_report)
                       │
                       │ 1:N
                       ▼
                   AI任务记录(ai_task)
```

### 关系说明

| 关系 | 倍数 | 说明 |
|------|------|------|
| user → case_case | 1:N | 一个用户可创建多个案件 |
| case_case → evidence | 1:N | 一个案件可上传多个证据 |
| case_case → ai_report | 1:N | 一个案件可生成多版报告（补充证据后重新分析） |
| ai_report → ai_task | 1:N | 一份报告由多个AI任务节点生成（意图识别/抽取/RAG/报告生成） |

> **为什么案件和报告是1:N而不是1:1？**
> 因为用户补充证据后AI需要重新分析，生成新版本报告。保留历史版本可以对比分析效果变化。

## 三、核心数据表设计

### 3.1 用户表 user

> 虽然核心是案件/证据/报告，但实际项目必须有用户体系。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 用户ID，主键 |
| username | varchar(50) | 用户名 |
| password | varchar(255) | 密码（加密存储） |
| phone | varchar(20) | 手机号 |
| avatar | varchar(255) | 头像URL |
| create_time | datetime | 创建时间 |
| update_time | datetime | 更新时间 |

```sql
CREATE TABLE `user` (
    `id`          BIGINT       PRIMARY KEY AUTO_INCREMENT,
    `username`    VARCHAR(50)  NOT NULL,
    `password`    VARCHAR(255) NOT NULL,
    `phone`       VARCHAR(20),
    `avatar`      VARCHAR(255),
    `create_time` DATETIME     DEFAULT CURRENT_TIMESTAMP,
    `update_time` DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

---

### 3.2 案件表 case_case（核心表）

> 一个用户可以创建多个租房纠纷案件。

**关系：** user 1 ──── N case_case

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 案件ID，主键 |
| user_id | bigint | 用户ID，外键 |
| case_title | varchar(100) | 案件名称 |
| case_type | varchar(50) | 纠纷类型（枚举） |
| status | varchar(20) | 案件状态（枚举） |
| description | text | 用户纠纷描述 |
| amount | decimal(10,2) | 涉及金额 |
| start_date | date | 租赁开始时间 |
| end_date | date | 租赁结束时间 |
| risk_level | varchar(20) | 风险等级（枚举） |
| ai_status | varchar(20) | AI分析状态 |
| create_time | datetime | 创建时间 |
| update_time | datetime | 更新时间 |

**case_type 枚举值：**

| 值 | 说明 |
|----|------|
| DEPOSIT | 押金纠纷 |
| RENT_CANCEL | 提前退租 |
| REPAIR | 维修责任 |
| CONTRACT | 合同风险 |

**status 枚举值：**

| 值 | 说明 | 触发条件 |
|----|------|---------|
| CREATED | 已创建 | 用户创建案件 |
| ANALYZING | 分析中 | AI开始处理 |
| WAITING | 等待补充 | AI追问，等待用户补充信息 |
| COMPLETED | 已完成 | 报告生成完毕 |

**risk_level 枚举值：**

| 值 | 说明 |
|----|------|
| LOW | 低风险 |
| MEDIUM | 中风险 |
| HIGH | 高风险 |

```sql
CREATE TABLE `case_case` (
    `id`          BIGINT        PRIMARY KEY AUTO_INCREMENT,
    `user_id`     BIGINT        NOT NULL,
    `case_title`  VARCHAR(100),
    `case_type`   VARCHAR(50)   NOT NULL COMMENT 'DEPOSIT/RENT_CANCEL/REPAIR/CONTRACT',
    `status`      VARCHAR(20)   DEFAULT 'CREATED' COMMENT 'CREATED/ANALYZING/WAITING/COMPLETED',
    `description` TEXT,
    `amount`      DECIMAL(10,2),
    `start_date`  DATE,
    `end_date`    DATE,
    `risk_level`  VARCHAR(20)   COMMENT 'LOW/MEDIUM/HIGH',
    `ai_status`   VARCHAR(20)   COMMENT 'PENDING/PROCESSING/DONE/FAILED',
    `create_time` DATETIME      DEFAULT CURRENT_TIMESTAMP,
    `update_time` DATETIME      DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (`user_id`) REFERENCES `user`(`id`)
);
```

### 3.3 证据表 evidence（核心差异功能）

> 这是租安AI区别于普通法律问答产品的核心：用户上传材料，AI自动分类、提取关键信息、评分。

**关系：** case_case 1 ──── N evidence

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 证据ID，主键 |
| case_id | bigint | 案件ID，外键 |
| file_name | varchar(255) | 文件名称 |
| file_url | varchar(500) | 文件存储地址 |
| file_type | varchar(50) | 文件格式（pdf/png/jpg...） |
| evidence_type | varchar(50) | 证据分类（枚举，AI自动识别） |
| ai_summary | text | AI生成的摘要 |
| importance_level | varchar(20) | 重要程度（枚举，AI评分） |
| extract_content | text | AI提取的关键信息（JSON） |
| upload_time | datetime | 上传时间 |

**evidence_type 枚举值：**

| 值 | 说明 | 典型文件 |
|----|------|---------|
| CONTRACT | 租赁合同 | PDF/拍照件 |
| PAYMENT | 支付记录 | 转账截图/收据 |
| CHAT | 聊天记录 | 微信截图 |
| IMAGE | 房屋照片 | 入住/退房照片 |
| VIDEO | 视频 | 退房视频 |
| OTHER | 其他 | 维修报价单等 |

**importance_level 枚举值：**

| 值 | 说明 |
|----|------|
| HIGH | 重要（如合同、转账记录） |
| MEDIUM | 一般（如聊天记录） |
| LOW | 低价值（如无关照片） |

```sql
CREATE TABLE `evidence` (
    `id`               BIGINT       PRIMARY KEY AUTO_INCREMENT,
    `case_id`          BIGINT       NOT NULL,
    `file_name`        VARCHAR(255),
    `file_url`         VARCHAR(500),
    `file_type`        VARCHAR(50)  COMMENT 'pdf/png/jpg...',
    `evidence_type`    VARCHAR(50)  COMMENT 'CONTRACT/PAYMENT/CHAT/IMAGE/VIDEO/OTHER',
    `ai_summary`       TEXT         COMMENT 'AI生成的证据摘要',
    `importance_level` VARCHAR(20)  COMMENT 'HIGH/MEDIUM/LOW',
    `extract_content`  TEXT         COMMENT 'AI提取的关键信息JSON',
    `upload_time`      DATETIME     DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (`case_id`) REFERENCES `case_case`(`id`)
);
```

**extract_content 字段示例（JSON）：**

合同类证据：
```json
{
  "租期": "2026-01-01 至 2026-12-31",
  "月租金": "3000元",
  "押金": "3000元",
  "违约条款": "提前退租扣1个月租金",
  "维修责任": "未明确约定"
}
```

聊天记录类证据：
```json
{
  "时间": "2026-07-20",
  "发送方": "房东",
  "关键内容": "墙面有损坏，扣除维修费2000元",
  "争议点": "房东单方面扣款，未提供维修凭证"
}
```

### 3.4 AI分析报告表 ai_report（核心输出）

> 一个案件对应多个报告版本。用户补充证据后AI重新分析，生成新版本。

**关系：** case_case 1 ──── N ai_report

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 报告ID，主键 |
| case_id | bigint | 案件ID，外键 |
| version | int | 报告版本号 |
| summary | text | 事实摘要（纠纷概览） |
| risk_analysis | text | 风险分析（等级+原因） |
| legal_basis | text | 法律依据（引用法条） |
| missing_evidence | text | 缺失证据提示 |
| action_plan | text | 行动建议（下一步操作） |
| ai_model | varchar(50) | 使用的模型名称 |
| token_usage | int | 消耗token数 |
| create_time | datetime | 生成时间 |

```sql
CREATE TABLE `ai_report` (
    `id`               BIGINT      PRIMARY KEY AUTO_INCREMENT,
    `case_id`          BIGINT      NOT NULL,
    `version`          INT         DEFAULT 1 COMMENT '报告版本号，补充证据后递增',
    `summary`          TEXT        COMMENT '纠纷事实摘要',
    `risk_analysis`    TEXT        COMMENT '风险评估：等级+原因',
    `legal_basis`      TEXT        COMMENT '法律依据：引用的法条',
    `missing_evidence` TEXT        COMMENT '缺失证据提示',
    `action_plan`      TEXT        COMMENT '行动建议：下一步操作步骤',
    `ai_model`         VARCHAR(50) COMMENT '使用的AI模型名称',
    `token_usage`      INT         COMMENT '本次生成消耗的token数',
    `create_time`      DATETIME    DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (`case_id`) REFERENCES `case_case`(`id`)
);
```

**报告各字段内容示例：**

```
summary:
  用户租赁合同到期后退房，房东以墙面损坏为由拒绝返还3000元押金。

risk_analysis:
  风险等级：中风险
  原因：
  1. 房东存在扣款理由
  2. 但目前缺少维修费用证明
  3. 用户已有聊天记录

legal_basis:
  《民法典》第710条：承租人按照约定的方法或者租赁物的性质使用租赁物，
  致使租赁物受到损耗的，不承担赔偿责任。
  《民法典》第713条：出租人应当履行租赁物的维修义务。

missing_evidence:
  还需要补充：
  □ 退房验收记录
  □ 房东维修凭证

action_plan:
  1. 要求房东提供维修凭证
  2. 保存双方沟通记录
  3. 尝试协商退款
  4. 协商不成拨打12345投诉
```

### 3.5 AI任务记录表 ai_task（效果评估核心）

> **这个表是AI产品经理的加分项。** 面试时会被问"怎么评估AI效果"，这个表记录了AI每次执行的输入输出和耗时，是效果评估的数据基础。

**关系：** case_case 1 ──── N ai_task（也可 ai_report 1 ──── N ai_task）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 任务ID，主键 |
| case_id | bigint | 案件ID |
| task_type | varchar(50) | 任务类型（枚举） |
| prompt | text | 输入Prompt（完整记录） |
| response | text | AI输出结果 |
| status | varchar(20) | 任务状态 |
| latency | int | 耗时（毫秒） |
| create_time | datetime | 执行时间 |

**task_type 枚举值：**

| 值 | 说明 | 对应Agent节点 |
|----|------|-------------|
| INTENT | 意图识别 | Agent节点1 |
| EXTRACT | 信息抽取 | Agent节点2 |
| COMPLETENESS | 完整度判断 | Agent节点3 |
| RAG | 知识检索 | Agent节点5 |
| REPORT | 报告生成 | Agent节点6 |
| EVIDENCE_OCR | 证据OCR识别 | 证据管理节点B |
| EVIDENCE_EXTRACT | 证据信息提取 | 证据管理节点C |
| ACTION_PLAN | 行动方案生成 | 行动指南节点I |

**status 枚举值：**

| 值 | 说明 |
|----|------|
| PENDING | 待执行 |
| RUNNING | 执行中 |
| SUCCESS | 成功 |
| FAILED | 失败 |

```sql
CREATE TABLE `ai_task` (
    `id`          BIGINT      PRIMARY KEY AUTO_INCREMENT,
    `case_id`     BIGINT      NOT NULL,
    `task_type`   VARCHAR(50) NOT NULL COMMENT 'INTENT/EXTRACT/COMPLETENESS/RAG/REPORT/EVIDENCE_OCR/EVIDENCE_EXTRACT/ACTION_PLAN',
    `prompt`      TEXT        COMMENT '输入Prompt完整内容',
    `response`    TEXT        COMMENT 'AI输出结果',
    `status`      VARCHAR(20) DEFAULT 'PENDING' COMMENT 'PENDING/RUNNING/SUCCESS/FAILED',
    `latency`     INT         COMMENT '耗时（毫秒）',
    `create_time` DATETIME    DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (`case_id`) REFERENCES `case_case`(`id`)
);
```

**ai_task表的价值（面试可讲）：**

| 用途 | 说明 |
|------|------|
| 效果评估 | 统计各task_type的成功率、准确率 |
| 性能优化 | 分析latency找出慢节点 |
| Prompt优化 | 对比不同prompt的response质量 |
| 成本核算 | 统计token消耗，优化调用频率 |
| Bad Case追踪 | 从FAILED记录中找典型问题 |

## 四、一次完整业务数据流

> 以下展示用户从创建案件到生成报告的完整数据流转过程。

### 场景：房东扣了3000元押金

```
用户输入："房东以墙面损坏为由拒绝退还3000元押金"
```

### Step 1：创建案件

```sql
-- case_case 表写入
INSERT INTO case_case (user_id, case_title, case_type, status, description, amount, ai_status)
VALUES (1, '押金纠纷-房东拒退3000元', 'DEPOSIT', 'CREATED',
        '房东以墙面损坏为由拒绝退还3000元押金', 3000.00, 'PENDING');
```

案件状态变化：

```
CREATED → ANALYZING → WAITING（需追问）→ ANALYZING → COMPLETED
```

### Step 2：AI意图识别（ai_task记录）

```sql
-- ai_task 表写入
INSERT INTO ai_task (case_id, task_type, prompt, response, status, latency)
VALUES (1, 'INTENT',
        '请识别以下纠纷的类型：房东以墙面损坏为由拒绝退还3000元押金',
        '{"问题类型":"押金纠纷","置信度":0.93}',
        'SUCCESS', 820);
```

### Step 3：用户上传证据

```sql
-- evidence 表写入（用户上传微信聊天截图）
INSERT INTO evidence (case_id, file_name, file_url, file_type, evidence_type, ai_summary, importance_level)
VALUES (1, '微信聊天截图.png', '/uploads/case1/chat_001.png', 'png', 'CHAT',
        '房东表示扣除维修费用，但未提供凭证', 'HIGH');
```

```sql
-- evidence 表写入（AI处理后的提取内容）
UPDATE evidence SET
  extract_content = '{"时间":"2026-07-20","发送方":"房东","关键内容":"墙面有损坏扣除维修费2000元","争议点":"未提供维修凭证"}'
WHERE id = 1;
```

### Step 4：AI生成报告

```sql
-- ai_report 表写入
INSERT INTO ai_report (case_id, version, summary, risk_analysis, legal_basis, missing_evidence, action_plan, ai_model, token_usage)
VALUES (1, 1,
        '用户租赁合同到期后退房，房东以墙面损坏为由拒绝返还3000元押金。',
        '风险等级：中风险。原因：房东存在扣款理由，但缺少维修费用证明，用户已有聊天记录。',
        '《民法典》第710条：承租人按照约定的方法使用租赁物致使损耗的，不承担赔偿责任。',
        '还需要补充：退房验收记录、房东维修凭证',
        '1.要求房东提供维修凭证 2.保存沟通记录 3.尝试协商 4.协商不成拨打12345投诉',
        'deepseek-chat', 2840);
```

```sql
-- ai_task 表记录报告生成过程
INSERT INTO ai_task (case_id, task_type, prompt, response, status, latency)
VALUES (1, 'REPORT',
        '基于以下信息生成纠纷分析报告：{结构化信息+检索结果}',
        '（完整报告内容）',
        'SUCCESS', 3500);

INSERT INTO ai_task (case_id, task_type, prompt, response, status, latency)
VALUES (1, 'RAG',
        '检索查询：租房押金退还 墙面损坏 正常损耗 维修责任',
        '[{"法条":"民法典第710条","相关度":0.92},{"法条":"民法典第713条","相关度":0.87}]',
        'SUCCESS', 120);
```

### Step 5：用户补充证据后重新分析

```sql
-- 用户补充了退房视频
INSERT INTO evidence (case_id, file_name, file_type, evidence_type, ai_summary, importance_level)
VALUES (1, '退房视频.mp4', 'mp4', 'VIDEO', '退房时墙面状态正常，无人为损坏', 'HIGH');

-- 案件状态重新变为分析中
UPDATE case_case SET status = 'ANALYZING', ai_status = 'PROCESSING' WHERE id = 1;

-- AI生成新版报告（version递增）
INSERT INTO ai_report (case_id, version, summary, risk_analysis, ...)
VALUES (1, 2, '...', '风险等级：低风险。用户已提供退房视频证明墙面正常...', ...);

-- 案件完成
UPDATE case_case SET status = 'COMPLETED', risk_level = 'LOW', ai_status = 'DONE' WHERE id = 1;
```

### 数据流全景图

```
用户创建案件                    AI处理                        用户补充
    │                            │                              │
    ▼                            ▼                              │
 case_case               ai_task(INTENT)                        │
 (status:CREATED)        ai_task(EXTRACT)                       │
    │                    ai_task(COMPLETENESS)                  │
    │                    ai_task(RAG)                           │
    ▼                    ai_task(REPORT)                        │
```

## 五、表设计的产品思维（面试话术）

### 5.1 简历怎么写

**不要写：** "设计数据库。"

**应该写：**

> 设计案件-证据-报告三层数据模型，实现租房纠纷从信息采集、证据管理到AI分析结果沉淀的完整数据闭环，并通过AI任务日志表支持模型效果评估和Prompt优化。

### 5.2 每张表体现的产品思维

| 表 | 产品思维 | 面试可讲 |
|----|---------|---------|
| case_case | 案件生命周期管理 | "我用status字段管理案件从创建到完成的全流程，包括AI追问的WAITING状态" |
| evidence | 证据AI化处理 | "证据表不只是存文件，还存了AI摘要、分类、重要度评分，让非结构化数据变成结构化" |
| ai_report | 版本化报告 | "报告用version字段做多版本管理，用户补充证据后AI重新生成，可以对比效果变化" |
| ai_task | AI效果可评估 | "专门设计AI任务记录表，记录每次调用的prompt/response/latency，这是效果评估和Prompt优化的数据基础" |

### 5.3 为什么这样设计（设计决策）

| 决策 | 原因 |
|------|------|
| 案件和报告1:N而非1:1 | 用户补充证据后AI需重新分析，保留历史版本可对比效果 |
| evidence表存AI处理结果 | 让证据从"一堆文件"变成"结构化信息"，后续可直接用于报告生成 |
| ai_task独立成表 | AI效果评估需要细粒度数据，每个Agent节点单独记录才能定位问题 |
| risk_level存在案件表 | 方便案件列表展示风险标签，不用每次查报告 |
| extract_content用JSON存 | 不同证据类型提取的字段不同，JSON比固定列更灵活 |
